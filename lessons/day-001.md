## 4. Explanation

### 4.1 What is a computer?
A **computer** is a machine that stores and follows instructions to transform input into output.
That's it. It doesn't "think" — it mechanically carries out very simple operations
(add, compare, move data) billions of times per second.

### 4.2 Hardware vs software
- **Hardware** = the physical parts you could touch: CPU, RAM sticks, SSD, keyboard, screen.
- **Software** = the instructions, which have no physical form: the operating system, Python, your
  script, a web browser.

Analogy: hardware is a **player piano**; software is the **punched roll of instructions** that
tells it which keys to strike. Same piano, different roll → different music.

### 4.3 What is a program?
A **program** is a set of instructions written to accomplish a task. You write it as **source
code** (text a human can read). The computer ultimately runs **machine code** (numbers the CPU
understands). Something has to bridge that gap — for Python, that's the **interpreter**.

### 4.4 What does "execute instructions" mean?
The CPU repeats a tiny cycle, forever, while powered:
1. **Fetch** the next instruction from memory.
2. **Decode** what it means.
3. **Execute** it (e.g. add two numbers, move data, compare).
4. Repeat.
This is the **fetch–decode–execute cycle**. You'll build an emulator of it later (project #3);
today just hold the mental picture.

### 4.5 The four roles
| Part | Role | Everyday analogy |
|------|------|------------------|
| **CPU** | Does the actual work: arithmetic, logic, control | The chef cooking |
| **RAM** | Fast, *temporary* working memory — erased on power off | The counter space the chef works on |
| **Storage (SSD/HDD)** | Slow, *persistent* memory — survives power off | The pantry/fridge |
| **I/O** | Gets data in and results out (keyboard, mouse, screen, network) | Waiter taking orders / serving plates |

Key idea: **RAM is fast but forgets; storage is slow but remembers.** A running program lives in
RAM; your files live in storage.

### 4.6 The execution chain (the heart of today)
When you run `print("Hello")`:
```
You type an instruction (the goal)
  → Source code:        print("Hello")           (text in a .py file)
  → Python interpreter: reads it, turns it into lower-level operations
  → Operating system:   manages memory, the screen, and scheduling for the interpreter
  → CPU instructions:   the actual fetch-decode-execute steps that do the work
  → Hardware operations: electrons move; the GPU/screen lights up pixels
  → Output:             "Hello" appears on your screen
```
Each layer **hides** the one below it. Today's whole purpose is to see that the layers exist — so
that later, when something breaks, you know there's a "below" to look into.

## 5. Concrete examples
- **Hardware doing one small thing:** adding `2 + 3` is a single CPU instruction operating on
  values held in tiny storage slots called registers.
- **Software hiding hardware:** `print("Hello")` looks like one action, but underneath it's many
  CPU instructions plus an OS call to put text on the screen.
- **RAM vs storage:** editing a document — your unsaved edits are in **RAM** (lose power = lose
  them); **Save** writes them to **storage** (survives power off). This is *why* "save your work."

## 10. Exercise D — Debugging exercise
> Goal: read an error message instead of fearing it.

Create `exercises/day01_bug.py` with **exactly** this (typo included):

1. Copy the **last line** of the error. What is it called (the error *type*)?
2. In your own words, what is the computer telling you?
3. Fix it so both lines print. What was the root cause — a hardware fault or a software mistake?
4. Which layer of the execution chain caught this error — the interpreter, the OS, or the CPU?
